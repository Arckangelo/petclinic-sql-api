| Data ausente (coluna fora do `INSERT`) | **recusa** | `INSERT INTO visits (pet_id, description) VALUES (7, 'Teste');` → `ERROR: null value in column "visit_date" of relation "visits" violates not-null constraint` |

| 29 de fevereiro em ano bissexto | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2020-02-29', 'Teste');` → `INSERT 0 1`, gravou `2020-02-29` |
| 29 de fevereiro em ano não bissexto | **recusa** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2021-02-29', 'Teste');` → `ERROR: date/time field value out of range: "2021-02-29"` |

| Palavra em inglês (`'yesterday'`) | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, 'yesterday', 'Teste');` → `INSERT 0 1`, gravou `2026-11-12` (rodado em 2026-11-13) |

| Pet que não existe | **recusa** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (9999, '2020-01-01', 'Teste');` → `ERROR: ... violates foreign key constraint "visits_pet_id_fkey"` |
| Trocar o pet de uma visita para um pet que não existe | **recusa** | `UPDATE visits SET pet_id = 9999 WHERE pet_id = 7;` → `ERROR: ... violates foreign key constraint "visits_pet_id_fkey"` |

`NOT NULL` recusa um valor **ausente**, mas aceita um texto **vazio**: são coisas diferentes
para o banco. O tipo `date` confere o calendário (inclusive ano bissexto), mas não se a
data faz sentido, e lê `dd/mm/aaaa` como mês/dia sem avisar: `04/03/2010` vira 3 de abril.
O banco também não compara a data da visita com o nascimento do pet. Nada aponta para
`visits`, então uma visita pode ser apagada livremente; a chave estrangeira só exige que
as visitas de um pet saiam antes dele.

## vet_specialties

A tabela liga os veterinários às suas especialidades. Um veterinário pode ter várias
especialidades, e uma especialidade pode ser de vários veterinários.

Legenda: **Nulo? Sim** = a coluna aceita ficar vazia; **Não** = preenchimento obrigatório.

"vet_specialties_specialty_id_fkey" FOREIGN KEY (specialty_id) REFERENCES specialties(id)

Regras que o banco **não** garante e que ficam por conta da aplicação, e as que ele garante.

| Situação | O banco... | Evidência |
|:---|:---:|:---|
| Ligação repetida (mesmo vet e mesma especialidade) | **recusa** | `INSERT INTO vet_specialties (vet_id, specialty_id) VALUES (2, 1);` → `ERROR: duplicate key value violates unique constraint "vet_specialties_vet_id_specialty_id_key"` |

As chaves estrangeiras impedem ligar a um vet ou especialidade que não existe, e impedem
apagar um vet ou uma especialidade enquanto houver ligação com eles.

O banco não confere se a senha é um hash: `'123'` foi gravado em texto puro. Ele
diferencia maiúsculas de minúsculas, então `Admin` e `admin` são usuários diferentes, e
aceita um username vazio. Como a chave primária é o `username` e a chave estrangeira de
`roles` não tem `ON UPDATE CASCADE`, um usuário com papéis não pode ser renomeado; só um
usuário sem papéis pode.

## roles

A tabela guarda os papéis (permissões) de cada usuário.

### Colunas

Legenda: **Nulo? Sim** = a coluna aceita ficar vazia; **Não** = preenchimento obrigatório.

| Coluna | Tipo | Nulo? | Padrão | Descrição |
|:---|:---|:---:|:---|:---|
| `id` | `integer` | Não | `generated by default as identity` | Identificador único (PK) |
| `username` | `varchar(20)` | Não | — | Usuário (FK → `users.username`) |
| `role` | `varchar(20)` | Não | — | Nome do papel |

### Índices

| Nome | Tipo | Colunas | Observações |
|:---|:---|:---|:---|
| `roles_pkey` | PRIMARY KEY | `id` | Chave primária |
| `uni_username_role` | UNIQUE CONSTRAINT | `role`, `username` | Impede o mesmo papel duas vezes para o mesmo usuário |

Não há índice só em `username`.

### Relacionamentos

Cada papel registrado é de um único usuário, e um usuário pode ter vários papéis
(`roles.username → users.username`). A ligação é pelo nome de login, não por um `id`.

```
"roles_username_fkey" FOREIGN KEY (username) REFERENCES users(username)
```

### Fora do banco

Regras que o banco **não** garante e que ficam por conta da aplicação, e as que ele garante.
Testado no banco do ambiente (docker compose), dentro de transações desfeitas com `ROLLBACK`.

| Situação | O banco... | Evidência |
|:---|:---:|:---|
| Papel inventado (`'qualquer coisa'`) | aceita | `INSERT INTO roles (username, role) VALUES ('admin', 'qualquer coisa');` → `INSERT 0 1` |
| Papel existente em minúsculas (`role_admin`) | aceita | `INSERT INTO roles (username, role) VALUES ('admin', 'role_admin');` → `INSERT 0 1` |
| Papel repetido para o mesmo usuário | **recusa** | `INSERT INTO roles (username, role) VALUES ('admin', 'ROLE_ADMIN');` → `ERROR: duplicate key value violates unique constraint "uni_username_role"` |
| Papel para um usuário que não existe | **recusa** | `INSERT INTO roles (username, role) VALUES ('naoexiste', 'ROLE_ADMIN');` → `ERROR: ... violates foreign key constraint "roles_username_fkey"` |

O banco não confere se o papel é um dos que a API conhece (`ROLE_OWNER_ADMIN`,
`ROLE_VET_ADMIN`, `ROLE_ADMIN`): qualquer texto de até 20 caracteres passa. Ele também
diferencia maiúsculas de minúsculas, então `role_admin` é aceito como um papel diferente
de `ROLE_ADMIN`. A regra `UNIQUE` em `(role, username)` impede o mesmo papel duas vezes
para o mesmo usuário.
