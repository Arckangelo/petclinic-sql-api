## owners

A tabela guarda os dados dos donos dos pets.

### Colunas

Legenda: **Nulo? Sim** = a coluna aceita ficar vazia; **Não** = preenchimento obrigatório.

| Colunas | Tipo | Nulo? | Padrão | Descrição|
|:---|:---|:---:|:---|:---|
| `id`| `integer` | Não | `generated by default as identity`| Identificador único (PK) |
| `first_name` | `text` | Sim | — | Primeiro nome |
| `last_name` | `text` | Sim | — | Sobrenome |
| `address` | `text` | Sim | — | Endereço |
| `city` | `text` | Sim | — | Cidade |
| `telephone` | `varchar(10)` | Não | — | Telefone |

### Índices

| Nome | Tipo | Colunas | Observações |
|:---|:---|:---|:---|
| `owners_pkey` | PRIMARY KEY | `id`| Chave primária |
| `owners_last_name_idx`| btree | `last_name`| Busca por sobrenome |

### Relacionamentos

Um dono pode ter vários pets, e cada pet tem um único dono (`pets.owner_id → owners.id`).

```
TABLE "pets" ... FOREIGN KEY (owner_id) REFERENCES owners(id)
```

### Fora do banco

Regras que o banco **não** garante e que ficam por conta da aplicação.
Testado no banco do ambiente (docker compose), dentro de uma transação desfeita com `ROLLBACK`.

| Situação | O banco... | Evidência |
|:---|:---:|:---|
| Dono só com telefone, sem nome nem sobrenome | aceita | `INSERT INTO owners (telephone) VALUES ('6085551023');` → `INSERT 0 1` |
| Telefone com letras | aceita | `INSERT INTO owners (telephone) VALUES ('abc');` → `INSERT 0 1` |
| Telefone com menos de 10 caracteres | aceita | `INSERT INTO owners (telephone) VALUES ('608555102');` → `INSERT 0 1` |
| Nome só com espaços | aceita | `INSERT INTO owners (first_name, telephone) VALUES ('   ', '6085551023');` → `INSERT 0 1` |
| Telefone vazio (`''`), mesmo com `NOT NULL` | aceita | `INSERT INTO owners (telephone) VALUES ('');` → `INSERT 0 1` |
| Telefone com 11 dígitos | **recusa** | `INSERT INTO owners (telephone) VALUES ('11987654321');` → `ERROR: value too long for type character varying(10)` |

O `varchar(10)` só limita o tamanho máximo. Por isso um celular brasileiro
com DDD (11 dígitos) é recusado, enquanto `'abc'` e `'608555102'` passam.

## pets

A tabela guarda os pets atendidos pela clínica.

### Colunas

Legenda: **Nulo? Sim** = a coluna aceita ficar vazia; **Não** = preenchimento obrigatório.

| Coluna | Tipo | Nulo? | Padrão | Descrição |
|:---|:---|:---:|:---|:---|
| `id` | `integer` | Não | `generated by default as identity` | Identificador único (PK) |
| `name` | `text` | Não | — | Nome do pet |
| `birth_date` | `date` | Não | — | Data de nascimento |
| `type_id` | `integer` | Não | — | Tipo do pet (FK → `types.id`) |
| `owner_id` | `integer` | Não | — | Dono do pet (FK → `owners.id`) |

### Índices

| Nome | Tipo | Colunas | Observações |
|:---|:---|:---|:---|
| `pets_pkey` | PRIMARY KEY | `id` | Chave primária |
| `pets_name_idx` | btree | `name` | Busca por nome |
| `pets_owner_id_idx` | btree | `owner_id` | Busca dos pets de um dono |

Não há índice em `type_id`.

### Relacionamentos

Cada pet tem um único dono, e um dono pode ter vários pets (`pets.owner_id → owners.id`).

Cada pet tem um único tipo, e um tipo pode valer para vários pets (`pets.type_id → types.id`).

Um pet pode ter várias visitas, e cada visita é de um único pet (`visits.pet_id → pets.id`).

```
"pets_owner_id_fkey" FOREIGN KEY (owner_id) REFERENCES owners(id)
"pets_type_id_fkey" FOREIGN KEY (type_id) REFERENCES types(id)
TABLE "visits" CONSTRAINT "visits_pet_id_fkey" FOREIGN KEY (pet_id) REFERENCES pets(id)
```
### Fora do banco

Regras que o banco **não** garante e que ficam por conta da aplicação, e as que ele garante.
Testado no banco do ambiente (docker compose), dentro de transações desfeitas com `ROLLBACK`.

| Situação | O banco... | Evidência |
|:---|:---:|:---|
| Nascimento no futuro | aceita | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('Teste', '2099-01-01', 1, 1);` → `INSERT 0 1` |
| Nascimento no ano 1800 | aceita | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('Teste', '1800-01-01', 1, 1);` → `INSERT 0 1` |
| Nome vazio (`''`), mesmo com `NOT NULL` | aceita | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('', '2020-01-01', 1, 1);` → `INSERT 0 1` |
| Data que não existe no calendário | **recusa** | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('Teste', '2020-02-30', 1, 1);` → `ERROR: date/time field value out of range: "2020-02-30"` |
| Dono que não existe | **recusa** | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('Teste', '2020-01-01', 1, 9999);` → `ERROR: ... violates foreign key constraint "pets_owner_id_fkey"` |
| Tipo que não existe | **recusa** | `INSERT INTO pets (name, birth_date, type_id, owner_id) VALUES ('Teste', '2020-01-01', 9999, 1);` → `ERROR: ... violates foreign key constraint "pets_type_id_fkey"` |
| Trocar o dono de um pet para um dono que não existe | **recusa** | `UPDATE pets SET owner_id = 9999 WHERE owner_id = 1;` → `ERROR: ... violates foreign key constraint "pets_owner_id_fkey"` |
| Apagar um dono que tem pets | **recusa** | `DELETE FROM owners WHERE id = 1;` → `ERROR: ... violates foreign key constraint "pets_owner_id_fkey" on table "pets"` |
| Apagar um pet que tem visitas | **recusa** | `DELETE FROM pets WHERE id = (SELECT min(pet_id) FROM visits);` → `ERROR: ... violates foreign key constraint "visits_pet_id_fkey" on table "visits"` (pet id 7) |

O tipo `date` confere se a data **existe** (30 de fevereiro é recusado), mas não se ela
**faz sentido** para um pet (2099 e 1800 passam). Já as chaves estrangeiras protegem a
ligação nos dois sentidos: não deixam criar ou alterar um pet apontando para um dono ou
tipo inexistente, nem apagar um dono ou um pet que ainda é referenciado.

## visits

A tabela guarda as visitas dos pets à clínica.

### Colunas

Legenda: **Nulo? Sim** = a coluna aceita ficar vazia; **Não** = preenchimento obrigatório.

| Coluna | Tipo | Nulo? | Padrão | Descrição |
|:---|:---|:---:|:---|:---|
| `id` | `integer` | Não | `generated by default as identity` | Identificador único (PK) |
| `pet_id` | `integer` | Não | — | Pet atendido (FK → `pets.id`) |
| `visit_date` | `date` | Não | — | Data da visita |
| `description` | `text` | Não | — | Descrição da visita |

### Índices

| Nome | Tipo | Colunas | Observações |
|:---|:---|:---|:---|
| `visits_pkey` | PRIMARY KEY | `id` | Chave primária |
| `visits_pet_id_idx` | btree | `pet_id` | Busca das visitas de um pet |

### Relacionamentos

Um pet pode ter várias visitas, e cada visita é de um único pet (`visits.pet_id → pets.id`).

Nenhuma tabela aponta para `visits`.

```
"visits_pet_id_fkey" FOREIGN KEY (pet_id) REFERENCES pets(id)
```
### Fora do banco

Regras que o banco **não** garante e que ficam por conta da aplicação, e as que ele garante.
Testado no banco do ambiente (docker compose), dentro de transações desfeitas com `ROLLBACK`.
O banco usa `DateStyle = ISO, MDY` (confirmado com `SHOW datestyle;`).

| Situação | O banco... | Evidência |
|:---|:---:|:---|
| Descrição vazia (`''`), mesmo com `NOT NULL` | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2020-01-01', '');` → `INSERT 0 1` |
| Descrição só com espaços | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2020-01-01', '   ');` → `INSERT 0 1` |
| Descrição ausente (coluna fora do `INSERT`) | **recusa** | `INSERT INTO visits (pet_id, visit_date) VALUES (7, '2020-01-01');` → `ERROR: null value in column "description" of relation "visits" violates not-null constraint` |
| Data ausente (coluna fora do `INSERT`) | **recusa** | `INSERT INTO visits (pet_id, description) VALUES (7, 'Teste');` → `ERROR: null value in column "visit_date" of relation "visits" violates not-null constraint` |
| Visita no futuro | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2099-01-01', 'Teste');` → `INSERT 0 1` |
| Visita antes do nascimento do pet (pet 7 nasceu em 1995-09-04) | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '1900-01-01', 'Teste');` → `INSERT 0 1` |
| 29 de fevereiro em ano bissexto | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2020-02-29', 'Teste');` → `INSERT 0 1`, gravou `2020-02-29` |
| 29 de fevereiro em ano não bissexto | **recusa** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2021-02-29', 'Teste');` → `ERROR: date/time field value out of range: "2021-02-29"` |
| Data no formato brasileiro (`dd/mm/aaaa`) | aceita, **mas lê como mês/dia** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '04/03/2010', 'Teste');` → `INSERT 0 1`, gravou `2010-04-03` (3 de abril, não 4 de março) |
| Palavra em português (`'ontem'`) | **recusa** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, 'ontem', 'Teste');` → `ERROR: invalid input syntax for type date: "ontem"` |
| Palavra em inglês (`'yesterday'`) | aceita | `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, 'yesterday', 'Teste');` → `INSERT 0 1`, gravou `2026-11-12` (rodado em 2026-11-13) |
| Visita duplicada (mesmo pet, data e descrição) | aceita | o mesmo `INSERT INTO visits (pet_id, visit_date, description) VALUES (7, '2020-01-01', 'Vacina');` duas vezes → `INSERT 0 1` nas duas |
| Pet que não existe | **recusa** | `INSERT INTO visits (pet_id, visit_date, description) VALUES (9999, '2020-01-01', 'Teste');` → `ERROR: ... violates foreign key constraint "visits_pet_id_fkey"` |
| Trocar o pet de uma visita para um pet que não existe | **recusa** | `UPDATE visits SET pet_id = 9999 WHERE pet_id = 7;` → `ERROR: ... violates foreign key constraint "visits_pet_id_fkey"` |
| Apagar as visitas de um pet e depois o pet | aceita | `DELETE FROM visits WHERE pet_id = 7;` → `DELETE 2`, depois `DELETE FROM pets WHERE id = 7;` → `DELETE 1` |

`NOT NULL` recusa um valor **ausente**, mas aceita um texto **vazio**: são coisas diferentes
para o banco. O tipo `date` confere o calendário (inclusive ano bissexto), mas não se a
data faz sentido, e lê `dd/mm/aaaa` como mês/dia sem avisar: `04/03/2010` vira 3 de abril.
O banco também não compara a data da visita com o nascimento do pet. Nada aponta para
`visits`, então uma visita pode ser apagada livremente; a chave estrangeira só exige que
as visitas de um pet saiam antes dele.
